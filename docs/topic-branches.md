# 话题分支图

公开 Pages 和本地读者页默认提供「分支图」，也可切换回「列表」。从话题展开不同陈述，点击标题或「阅读陈述与来源」进入正文；文章详情会显示同话题分支和当前陈述位置。Pages 的链接保留目录视图、主题和搜索条件，刷新或返回仍可恢复。

每条陈述独立保留来源类别、适用范围、核验状态与阅读入口。同话题的不同陈述并列展示；针对一篇陈述的补充信息显示在该陈述下面，也可继续展开补充的补充。连线表示话题归属或明确记录的补充关系，不代表继承父陈述的核验结论。有关联理由的内容另外显示在「横向关联」中，不能将它理解为自动确认的支持、反对或修订关系。大量内容会逐步显示，当前选中路径始终可见。

## 收录不同说法

读者从具体文章的「补充/更正这篇」入口选择个人经验，说明与现有描述不同的情况、时间、校区和依据，在 GitHub 最终确认投稿。维护者可以把同话题的不同陈述收录为不同的 answer 实体：使用不同 `id`、`slug` 和独立修订，并指定相同 `topicId`。每条陈述仍按现有证据和审核发布流程处理；只有更正同一陈述的内容时才追加其修订，不能为了收录另一种经历而覆盖原陈述。

现有 runtime 内容交换格式的 `links` 可记录两篇陈述之间的公开关联，例如：

```json
{
  "id": "arrival-experiences-related",
  "from": "arrival-experience-a",
  "to": "arrival-experience-b",
  "reason": "两篇描述同一入学事项在不同校区和时间的经历，可对照适用条件。"
}
```

示例 ID 仅用于说明，不是生产内容。`reason` 是公开说明，不能填写内部审核意见。runtime 0.3.0 公开投影将这些关系统一标记为 `related`；两端都在本次公开内容中才显示。新陈述不会因为同话题关系而自动发布，GitHub 投稿也不会自动进入内容库。

## 将补充信息放到陈述下面

补充信息仍使用独立的 answer 实体、修订、来源和审核记录。在它当前修订的 `data` 中填写可选的 `supplementTo`，值为被补充陈述的 **实体 ID**，并使用与父陈述相同的 `topicId`。例如：

```json
{
  "id": "arrival-login-extra-r1",
  "entityId": "arrival-login-extra",
  "data": {
    "topicId": "topic-systems",
    "supplementTo": "arrival-login-main"
  }
}
```

这只是关系字段示意；实际修订仍需完整正文、适用范围与对应引文。`supplementTo` 可指向另一条补充，形成「话题 → 陈述 → 补充 → 进一步补充」。它不能指向自身、其他话题或不存在的陈述，也不能组成循环。省略该字段时，该陈述仍作为话题下的独立分支。`parentRevisionId` 表示同一实体的版本历史，不用于补充关系。

每条补充单独判断来源、适用范围和公开状态。只有父陈述及整条祖先路径都在当前公开集合中，读者页才显示补充分支；祖先被隐藏、来源撤回，或其草稿既未审核发布也未获 Pages 精确收录授权时，其补充也随之移出本次公开集合，不会变成没有上下文的独立陈述。收录通道仍需逐条选定补充修订，不能通过指定父陈述自动收录补充，也不能借补充关系获得人工核验标记。

审核列表会标明补充对应的父陈述及其 runtime 发布状态。发布校验关系结构：父陈述必须存在、处于同一话题且整条关系无循环，违反时整批不保存。父陈述可以仍未审核，补充可单独审核发布；审核确认保留原补充关系，只为实际通过的陈述生成不可变确认修订。父陈述与补充也可以在同一批次审核发布，提交顺序不影响结果。

例如，Pages 已明确收录的 AI 初版可以继续显示「资料整理初版／尚未人工核验」，其补充单独审核后显示自己的已审核状态。导出会将二者放在同一补充分支中，不会因为补充通过审核而给父陈述补写核验时间。在不含该收录通道的本地读者页，父陈述仍未公开时，这条补充分支暂不显示。

搜索或范围筛选命中补充时，分支图保留公开的祖先路径作为上下文。祖先不会被算作命中结果，其适用范围和核验状态也不会覆盖补充本身。

## 实现与可见性

- 使用固定 core 0.3.0 的 `buildBranchTree`、`branchPath` 和 `visibleBranchRows`，主树指定 `direction: outgoing`、`relationTypes: [branch]`。上游仍是未提交的工作树产物，来源与哈希记录在 [vendor/README.md](../vendor/README.md)。配套 runtime 保持 0.3.0，存储和发布协议未改。
- `community/ui/branch-model.js` 把已经可公开的答案适配为「指南 → 话题 → 陈述 → 补充」；`branches.js` 和 `branches.css` 在两个读者页面共用。上游包代码从安装目录提供，未复制到业务源码维护。
- 本地 `/api/guide/branches` 返回 `{ answers, contextAnswers, links }`。`answers` 是匹配搜索和范围的公开答案；`contextAnswers` 只补足未在结果中的公开祖先，无筛选时为空。普通 `/api/guide/answers` 不增加上下文结果。详情重新读取完整公开集合，不受目录搜索结果影响。历史修订不会被错误标成当前分支。
- 公开 answer DTO 和 Pages 快照答案增加可选 `supplementTo` 字段，快照严格校验字段类型、父节点存在、同话题和无循环。`links` 仍限制为 `id/from/to/type/reason`，校验两端是快照中的公开文章。旧快照省略这些可选字段仍可构建；76 篇已收录初版仍能按话题生成分支，无须改动正文或核验记录。
- 导出依旧从平台公开投影及明确授权的资料收录投影获得内容和关联。隐藏、撤回来源、后续审核处置及精确修订清单都影响下一次导出；不从私件、原始备份或未授权草稿生成公开节点。静态站点的后续变化仍需同步发布。
- Pages 构建只额外复制共享界面文件和安装包的 `core/index.js`、`core/branches.js`、`core/LICENSE`；目录中的未知文件仍会令构建失败。本地服务由网关提供 `/extensions/core/*`，运行库 UI 构建仍由平台管理。

运行 `npm test`、`npm run test:platform`、`npm run test:browser`、`npm run build` 和 `npm run build:pages` 验证。浏览器测试需要可用的 Playwright 与 Chromium/Edge；可通过 `PLAYWRIGHT_PACKAGE` 指向已安装的 Playwright 包入口。
