# 阶段 1 本地运行与运维手册

> 历史资料：以下描述旧 Vinext/D1 应用，不是当前运行入口。当前手册见 [底座运行与迁移](platform-runtime.md)。旧源码基线保留于 [b110fa9 的 apps/web](https://github.com/BillShiyaoZhang/xjtlu-unofficial-guide/tree/b110fa955931a7679413662b462e0da28fd96586/apps/web)，本地旧目录仅供迁移对照及回滚资料保管。

- 状态：可运行基线 v1
- 更新日期：2026-08-29
- 适用范围：低风险、编辑驱动的阶段 1 产品

## 1. 部署边界

本项目**不部署到 OpenAI Sites**。仓库中的 `.openai/hosting.json` 和 Sites 构建插件只承担现有脚手架与本地绑定适配，不代表发布授权，也不应成为上线目标。

当前已验证的运行方式是 `apps/web` 下的本地 Vinext/Wrangler 服务与项目内 D1 数据。若需要让真实试点参与者访问，运营方应选择并负责自己的基础设施，例如受控的校内主机、私有云或兼容的 Worker/D1 环境，并自行完成域名、HTTPS、访问控制、监控、备份和数据处理协议。将存储迁移到 PostgreSQL 或其他平台是单独的工程项目，不能仅修改环境变量后假定兼容。

以下情况都不属于“本地启动”授权：把开发端口直接暴露到互联网、复用个人电脑承载正式试点、使用演示数据承载真实用户，或把 `.wrangler`、`.env.local`、备份上传到公共共享空间。

## 2. 服务目标与责任边界

阶段 1 的恢复目标是：

- RPO（最多可丢失的数据时间）：不超过 24 小时。
- RTO（从确认灾难到恢复核心只读与处置能力）：不超过 4 小时。
- 每天至少生成并校验一份数据库备份；调度间隔应留出失败重试余量，使校验通过时间距当前始终不超过 24 小时。
- 每月至少完成一次隔离恢复演练；成功演练距当前不得超过 31 天。

运营方需在上线前指定值班负责人、内容负责人、安全/隐私负责人和基础设施负责人，并把联系方式放在其受控的值班系统中。本仓库不虚构姓名、组织主体、法务意见或联系方式。上述责任人未确定时，不得对外开放真实试点。

## 3. 环境与密钥

复制示例文件后，仅在受限的本地密钥文件或所选基础设施的密钥管理服务中填写值。不要提交 `.env.local`，不要把密钥放入前端构建参数、工单正文、聊天记录或备份说明。

```bash
cd apps/web
npm install
cp .env.example .env.local
umask 077
npm run dev
```

生产/真实试点必须显式配置以下项目：

| 变量 | 用途 | 要求 |
| --- | --- | --- |
| `EDITOR_PASSWORD_PEPPER` | 编辑密码哈希的服务端 pepper | 独立随机值，至少 32 字符 |
| `EDITOR_MFA_KEY_V1` | 编辑 TOTP 秘钥的静态加密密钥 | 独立随机值，至少 32 字符 |
| `EDITOR_RATE_LIMIT_SECRET` | 持久限流桶的 HMAC 密钥 | 独立随机值，至少 32 字符 |
| `PRIVATE_INTAKE_KEY_V1` | 私有线索载荷的 AES-GCM 静态加密密钥 | 独立随机值，至少 32 字符 |
| `EDITOR_BOOTSTRAP_EMAIL` | 首个具名管理员邮箱 | 只在首次建号时配置 |
| `EDITOR_BOOTSTRAP_NAME` | 首个具名管理员显示名 | 只在首次建号时配置 |
| `EDITOR_BOOTSTRAP_PASSWORD` | 首次管理员密码 | 14–200 字符，只在首次建号时配置 |
| `EDITOR_BOOTSTRAP_TOTP_SECRET` | 首次管理员 TOTP Base32 秘钥 | 16–128 个 `A-Z2-7` 字符，只在首次建号时配置 |
| `PILOT_SECRET` | 试点伪名、会话与不透明搜索视图的派生密钥 | 独立随机值，至少 32 字符 |
| `MAINTENANCE_SECRET` | 内部维护和运维证明接口的 Bearer 凭证 | 独立随机值，至少 32 字符 |
| `PUBLIC_ORIGIN` | canonical 与同源校验基准 | 真实试点必须是无尾斜杠的 HTTPS origin |
| `PILOT_WINDOW_START/END` | 四周试点统计冻结窗口 | 成对配置，带时区，结束时间不包含在窗口内 |

这些密钥不得相互复用。真实试点还必须保持：

```dotenv
EDITOR_ENABLE_LEGACY_LOGIN=false
EDITOR_LOGIN_SECRET=
EDITOR_SESSION_SECRET=
SEED_DEMO_CONTENT=false
```

本地开发服务会为了迁移旧演示流程提供兼容默认值；不要把开发默认值当作真实试点配置。以 `/editor/operations` 的上线检查为准，而不是以“页面能打开”为准。

## 4. 首次具名管理员

1. 在空数据库上配置四项安全密钥和四项 `EDITOR_BOOTSTRAP_*` 值。
2. 启动服务，访问 `/editor/login`，用配置的邮箱、密码和认证器 6 位验证码登录。首次登录会原子创建具名账号、TOTP 因子和全部管理角色。
3. 进入 `/editor/accounts` 创建日常使用账号，按职责授予最小角色。不要让所有编辑长期持有 `account_admin` 或 `operations_admin`。
4. 进入 `/editor/security` 核对当前会话，并测试注销与会话撤销。
5. 确认具名管理员可重新登录后，从运行环境删除全部 `EDITOR_BOOTSTRAP_*` 值并重启。
6. 在 `/editor/operations` 确认“至少一个具名编辑账号”和“共享编辑入口已关闭”均通过。

首个账号不会因为环境变量被删除而消失。反过来，保留 bootstrap 密码会扩大泄露面；完成建号后必须移除。新建账号生成的恢复码只显示一次，应由账号本人放入独立密码管理器，不得由管理员集中收集。

角色用途如下：

| 角色 | 最小职责 |
| --- | --- |
| `content_editor` | 创建答案卡和修订草稿 |
| `content_reviewer` | 发布修订、调整公开状态、维护目录与来源处置 |
| `pilot_operator` | 管理受邀成年试点会话 |
| `safety_reviewer` | 读取和处置报告、私有线索 |
| `account_admin` | 创建、停用账号和调整角色 |
| `operations_admin` | 查看健康、维护、备份和恢复证据 |

## 5. 启动、停止与日常检查

### 5.1 启动前

- 确认当前版本通过 `npm run lint`、`npm run typecheck`、`npm test` 和 `npm run build`。
- 确认数据库和密钥文件仅服务账号可读，磁盘与备份已加密。
- 确认 `PUBLIC_ORIGIN` 与实际 HTTPS origin 完全一致。
- 确认演示种子关闭、共享编辑入口关闭、bootstrap 变量已移除。
- 确认最近 24 小时备份和最近 31 天恢复演练有效。

### 5.2 启动后

- 请求 `GET /v1/health`。HTTP 200 且 `status=ok` 表示迁移、私有数据保留和公开来源不变量通过；HTTP 503 必须按故障处理，不能只在负载均衡器中忽略。
- 登录 `/editor/operations`，确认全部上线检查通过，并查看逾期报告、逾期私有线索、活跃编辑会话和最近运行记录。
- 抽查公开搜索、答案详情、来源链接、报告提交和编辑处置各一条，不使用真实个人信息作为测试内容。

### 5.3 停止

计划停止前先结束编辑写入，完成一致性备份并记录校验和。不要在数据库正在写入时直接复制底层文件。停止后让反向代理返回维护页，不要回退到旧的、可能不兼容数据库的应用实例。

## 6. 每日 maintenance

由所选基础设施的独立调度器每天至少调用一次：

```bash
curl -X POST https://<your-origin>/v1/internal/maintenance \
  -H 'Authorization: Bearer <maintenance-secret>'
```

调用成功会写入 `maintenance_runs`，并返回本次清理与安全处置摘要。任务负责：

- 清空到期的私有研究线索载荷及关联；
- 删除到期的查询/打开/分享等短期事件；
- 清理过期限流窗口；
- 撤销过期编辑会话；
- 检测当前公开答案是否引用了非批准、非公开或权利到期来源，并通过受控工作流隐藏受影响答案。

运维规则：

- 调度器只持有 `MAINTENANCE_SECRET`，不得持有编辑账号密码。
- 失败立即告警；连续两次失败或最近成功超过 26 小时，进入事件响应。
- 不用“再次调用直到成功”掩盖持续故障；保留请求 ID 和失败时间，在 `/editor/operations` 核对运行记录。
- maintenance 是数据保留和来源安全兜底，不替代报告队列与人工复核。

## 7. 每日备份与证明回调

备份由所选基础设施在应用之外完成。必须使用该存储支持的一致性快照/导出机制；不要对运行中的 SQLite/D1 文件做普通文件复制。备份应加密、限制读取权限，并设置独立于生产账号的删除保护。

每次备份流程：

1. 生成一致性快照，记录外部快照 ID；外部 ID 不含参与者姓名或问题正文。
2. 对完成的备份计算 SHA-256，并执行可读取/完整性校验。
3. 设置保留到期时间；备份间隔建议不超过 20 小时，给重试留出余量，并保证任意时刻有一个覆盖最近 24 小时的已验证备份。
4. 使用固定运行 ID 回调应用。应用只保存快照引用的 SHA-256，不保存外部位置或访问凭据。

成功证明示例；所有时间均为 Unix 秒：

```bash
curl -X POST https://<your-origin>/v1/internal/backup-runs \
  -H 'Authorization: Bearer <maintenance-secret>' \
  -H 'Content-Type: application/json' \
  --data '{
    "id": "backup-2026-08-29",
    "status": "succeeded",
    "snapshotReference": "<provider-snapshot-id>",
    "checksumSha256": "<64-lowercase-hex-chars>",
    "startedAt": 1787932800,
    "completedAt": 1787933100,
    "expiresAt": 1790525100,
    "verifiedAt": 1787933100,
    "details": {"policy": "daily-encrypted"}
  }'
```

可以先用同一个 `id` 上报 `running`，结束后再上报 `succeeded` 或 `failed`。只有包含非空快照引用、64 位小写十六进制 SHA-256 和校验时间的成功记录才计入 24 小时上线检查。证明回调成功不等于备份真实可恢复，必须配合恢复演练。

具体保留周期必须由运营方结合恢复需求和私有数据期限批准，不能因为备份而无限延长用户数据寿命。备份到期删除也要覆盖复制品、临时恢复实例和供应商回收站；从较旧备份恢复后，必须在开放访问前先运行 maintenance，使已经到期的载荷再次被清除。

## 8. 月度恢复演练

至少每 31 天执行一次，且必须恢复到与生产隔离的环境：

1. 选择一个最近成功且校验通过的 `backupRunId`。
2. 在隔离实例恢复数据，不覆盖生产数据库。
3. 校验所有迁移存在，执行数据库外键/完整性检查。
4. 先运行 maintenance 重新执行到期删除与来源安全处置，再用只读方式验证公开搜索、答案详情、来源可见性和编辑登录数据结构；测试账号与请求不得连接真实通知渠道。
5. 记录从宣布恢复到核心读取通过的耗时；必须不超过 4 小时。
6. 销毁隔离恢复实例及临时密钥，并按相同数据保留要求处理日志。
7. 把结果回调到生产运维证据库。

成功证明示例：

```bash
curl -X POST https://<your-origin>/v1/internal/recovery-drills \
  -H 'Authorization: Bearer <maintenance-secret>' \
  -H 'Content-Type: application/json' \
  --data '{
    "id": "drill-2026-08",
    "backupRunId": "backup-2026-08-29",
    "status": "succeeded",
    "startedAt": 1787934000,
    "completedAt": 1787937600,
    "foreignKeyCheckPassed": true,
    "smokeCheckPassed": true,
    "details": {"environment": "isolated", "rtoSeconds": 3600}
  }'
```

成功演练必须关联已记录备份，并同时通过外键和核心读取检查。任何失败演练都要保留失败记录、开修复项，并在修复后重新演练；不能把失败记录改写成成功而省略重试证据。

## 9. 密钥轮换

所有密钥至少每 180 天复核一次，在人员离岗、权限边界变化或疑似泄露时立即处理。轮换前先完成备份和恢复演练，并保存当前角色清单与调度配置。

| 密钥 | 当前轮换方式与影响 |
| --- | --- |
| `MAINTENANCE_SECRET` | 先准备调度器新值，在短维护窗内同步切换应用与调度器；旧值立即失效，随后手动验证 maintenance 与证明回调 |
| `EDITOR_RATE_LIMIT_SECRET` | 可在维护窗切换；现有限流桶不会映射到新值，切换后应加强观察登录与提交告警 |
| `PILOT_SECRET` | 会影响伪名查找、既有参与者会话和不透明搜索视图；只在试点批次之间轮换，事件轮换时按数据恢复事件处理并通知停止使用旧会话 |
| `EDITOR_PASSWORD_PEPPER` | 现版本没有双 pepper 在线迁移；改变后既有密码无法验证。必须通过经过测试的软件迁移/账号重新置备完成，不能直接替换环境变量 |
| `EDITOR_MFA_KEY_V1` | 现版本只读取 v1 密钥；改变后既有 TOTP 密文无法解密。必须先增加版本化解密与重新加密迁移，或在受控停机中重新置备全部因子 |
| `PRIVATE_INTAKE_KEY_V1` | 现版本只读取 v1 密钥；改变后未到期私有载荷无法解密。必须先增加双密钥读取和重加密迁移，完成校验后再撤下旧密钥 |

编辑密码或 MFA 密钥疑似泄露时，先在账号管理中停用受影响账号并撤销会话，暂停编辑写入；在完成迁移/重新置备前保持 fail-closed。不要为追求在线轮换临时恢复共享编辑口令。

## 10. 上线检查

以下项目全部通过才可开始真实、邀请制阶段 1 试点：

- [ ] 部署目标是本地或运营方自选基础设施，不是 OpenAI Sites。
- [ ] 已确定运营主体、值班、内容、安全/隐私和基础设施责任人；联系方式存放在受控系统。
- [ ] 有准确的隐私、版权、报告和申诉说明，且未虚构主体或联系人。
- [ ] `PUBLIC_ORIGIN` 是真实 HTTPS origin；代理不记录完整 query string。
- [ ] 具名账号、MFA、最小角色、会话撤销已实测；bootstrap 变量与共享入口已关闭。
- [ ] 所有安全密钥独立、进入密钥管理服务，演示种子关闭。
- [ ] maintenance 每日调度并有失败告警。
- [ ] 24 小时内有校验备份，31 天内有成功隔离恢复演练，实测 RPO/RTO 达标。
- [ ] `/v1/health` 返回 200，`/editor/operations` 全部检查通过且无逾期私有载荷/失效公开来源。
- [ ] 报告和私有线索队列有人值班，并完成一次从提交到处置的演练。
- [ ] 内容切口、来源权利、双人抽查、高影响内容关闭和退出条件均已冻结。
- [ ] 自动化测试、生产构建与运行时依赖审计通过。

## 11. 故障响应

### 11.1 分级

- P0：私有数据泄露、编辑账号接管、生产数据不可用、错误来源仍支撑高影响结论。
- P1：健康检查持续失败、maintenance 超过 26 小时未成功、备份超过 24 小时、报告严重超 SLA。
- P2：单个答案错误、单个来源失效、非核心页面或指标异常。

### 11.2 通用步骤

1. 记录发现时间、影响面、当前版本和请求 ID；不要在公开群聊粘贴私有内容。
2. 先止损：暂停写入/试点邀请，撤销账号会话，或通过来源处置/答案隐藏让不安全内容立即下线。
3. 保护证据：保留追加式审计、运行记录和相关校验和；不要直接改写历史修订。
4. 判断数据是否需要恢复、密钥是否需要轮换、受影响人员是否需要由运营主体通知。
5. 修复后执行健康、核心读写、权限、maintenance 和来源安全检查。
6. 记录时间线、根因、恢复点、实际 RPO/RTO 和防复发项。

来源撤回或权利到期时，应先在编辑目录把来源标为 `under_review`、`withdrawn` 或 `unavailable`；服务会在同一事务中隐藏所有受影响的当前公开卡片并留下工作流记录。内容修正通过创建并发布新修订完成，不覆盖旧修订。

## 12. 回滚与恢复

- 应用回滚前先比较目标版本与当前数据库迁移。数据库迁移是追加式的，不能假定支持向下迁移。
- 仅当旧应用明确兼容当前数据库时，才回滚应用二进制；否则保持维护页并以前向修复为主。
- 内容回滚不是删除历史：发布一份引用充分的新修订，或先隐藏整卡/处置来源。
- 数据库恢复必须从已验证备份恢复到隔离环境，完成完整性和核心读取检查后再决定切换。不要直接覆盖唯一生产副本。
- 切换恢复实例前记录恢复点和预期数据损失，验证其不超过 24 小时；若超过，保持只读并由运营责任人决定下一步。
- 恢复后轮换可能暴露的凭证、撤销旧编辑会话、补跑 maintenance，并重新生成备份证明。

本手册定义的是软件与运营最低闭环，不构成法律、隐私或学校政策意见。运营主体应根据实际部署地点、参与者和数据处理活动完成独立审查。
