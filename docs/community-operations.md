# 校园共建：当前运营流程

更新：2026-09-10。本页描述本轮代码实现后的工作方式；代码、话题配置和公开快照完成部署后，线上页面才会相应更新。本文不表示已经发出邀请、产生真实投稿或发布活动。

平台把公开讨论和编辑整理连接起来：读者可在站内写一小段分享，再到 GitHub 最终提交；网站读取公开 Issue 和回复；维护者把有用的贡献整理进带来源的资料。讨论被引用、Issue 被关闭和内容经过核验是不同事情。

本地首批冷启动现已新增 16 条带公开来源的话题，与原 3 条编辑提问分组呈现。来源摘要附原链接和读取状态；它们不算 GitHub 投稿。导入、时效、纸条／小红书的访问结果和独立样例预览见 [冷启动数据说明](cold-start-data.md)。配置经正常仓库流程部署后才会出现在在线页面。

## 1. 当前配置与入口

首页的三条编辑提问来自 [community-topics.json](../community/community-topics.json)：

| 提问 | 稳定 ID | 关联资料分类 |
| --- | --- | --- |
| 你最希望开课前有人告诉你的那件事 | `before-your-first-class` | `topic-study` |
| 有什么校园资源，你希望早点知道？ | `wish-i-knew-campus-resources` | `topic-services` |
| 读硕士的第一个月，什么最让你困惑？ | `masters-first-month-questions` | `topic-arrival` |

它们是编辑邀请大家回答的问题，没有自带用户回答、评论数、参与人数或活动事实。分类下现有资料条数表示“相关资料”，不是这道问题已经收到的回答数。另有“校园里，有什么新消息？”入口，以及从现有分类生成的话题入口；首页不会将全部分类铺成一组虚构的热门讨论。

修改问题时保留已有 `id`，否则旧投稿的关联标记不会自动迁移。`catalogTopicId` 必须指向当前公开分类。新话题的字段由 [topic-model.js](../community/pages-ui/topic-model.js) 校验；配置只接受显式公共字段，不接收内部备注、私件、评论数或伪造热度。`createdAt` 可省略；填写时用真实话题发布时间，不借它表示活动发生时间。

`npm run build:pages` 会将通过校验的配置单独输出为 `community/pages-dist/community-topics.json`，并复制共建界面模块。缺少输入配置时输出空话题列表；非法配置、未知分类或符号链接输入会使构建失败，不会静默发布。构建本身不会向外部署。

## 2. 原始分享与回复怎样进入网站

1. 从话题点击分享入口，写正文并确认内容及 GitHub 用户名可以公开。来源性质、校区、学期／发生时间、链接和标题可随后补充；个人经历不要求附官方证明。
2. 新分享会生成完整 Issue 草稿，包含精确话题标记 `<!-- xjtlu-topic:话题ID -->`。用户打开 GitHub、登录并确认提交后，才实际创建 Issue。不要在编辑时删除这个标记，也不要把它放进引号或代码块。
3. 回复已有分享时，站内提供完整回复文本和原讨论链接。用户复制、到 GitHub 评论框粘贴并提交；当前不保证 GitHub 评论能自动预填。
4. 内容过长时保留完整文字，提供复制路径，不截断投稿。轻量分享可以主动“保存到本机”、恢复和清除草稿；保存只作用于这台设备，清除草稿不会删除 GitHub 上的内容。
5. 返回话题可刷新讨论。网站按页读取配置仓库的公开 Issue，排除 Pull Request，匹配精确话题标记；兼容旧表单中位于“关联文章”段落的准确文章 ID。随便提到话题名、文章标题或链接，不会自动建立归属。

站内不会根据点击提交链接就宣布“发布成功”，也不能确认某位用户是否完成了 GitHub 提交。实际读到的公开投稿会显示 GitHub 署名、发布／更新时间、原帖链接和实际回复数。读取时间表示这次加载时间，不是消息发生时间。

讨论加载失败、限流、尚未读完分页和确实没读到匹配投稿，必须保持不同提示。遇到失败可刷新或到 GitHub 查看；不要用“还没有人分享”掩盖网络错误。首次页面没有匹配也不代表全部历史为空，可继续读取较早页面。

当前没有站内账号提交、自动私信、跨设备草稿同步或自动通知贡献者。网站只读取公开讨论供展示，不把原始 Issue 自动导入运行库，也不自动将其变成核验过的资料。

## 3. 编辑怎样把贡献变成带来源的整理

先在原讨论中补齐影响理解的条件：发生时间、校区、课程版本、作者亲历还是转述。可以保留不同经验与未知之处，不必为结案选出一种统一说法。几个人的案例不能写成全体学生的分布。

整理时按以下步骤操作：

1. 选定有用的具体贡献，复制它的公开永久链接。引用 Issue 正文使用该 Issue 的地址；引用一条回复使用那条回复的 `#issuecomment-...` 链接。不能把整串回复中某个人的说法都归给 Issue 发起者。
2. 按现有内容工作流建立来源及答案修订，把具体事实句与相应来源关联。描述个人经历时写清“提供者在某时间／条件下的经历”，不将它改写成全校规则。来源链接只出现在正文中不足以建立双向引用，必须进入修订的 citations。
3. 对直接向本项目提供的经历，在 [source-overrides.json](../community/source-overrides.json) 按准确 URL 登记 `user_provided` 及分类依据；用户提供的学校通知链接仍属于学校官方材料。来源类别和核验状态各自保留，详见 [来源分类](source-categories.md)。
4. 使用独立陈述保留不同经历；更正同一条整理时追加新修订。针对已有陈述的补充可用 `supplementTo` 指向其实体 ID，不能用版本父子关系冒充补充。具体字段及公开条件见 [话题分支说明](topic-branches.md)。
5. 按实际完成的来源核对与审核结果处理发布。编辑概括、关闭 Issue、关联来源都不会自动填写人工核验时间。既有 76 篇资料的收录清单不自动授权未来草稿。
6. 将公开资料同步成新快照并部署，再检查整理中的原文链接和原帖旁的引用去向。可以在原 Issue 补充整理链接，让参与者看得到结果；这一评论需要维护者实际发送，网站不会替编辑自动留言。

已公开的资料引用精确 Issue／回复 URL 后，网站在读到该原文时会显示“这条原文已被引用”及相关资料链接；资料端也保留原始来源回链。这是引用关系，不表示原文已经通过审核，更不表示整理与原作者逐字一致。话题页同分类的背景资料仍可能来自别的讨论，应结合标题和原始链接判断。

话题页根据实际读到的原帖建立“目前整理”的关联；同分类的另一道问题不会自动成为本题的总结。尚无回答时先显示分享输入，有回答但没有关联整理时先显示讨论，形成关联整理后才将整理放到前面。读者正在输入时不会为了更新排列移动输入区；原始讨论和相关背景资料始终保留。

作者在 GitHub 修改原贡献，不会自动重写已经发布的整理。维护者应检查含义变化并追加适当修订，保留原意、署名与版本关系。需要更正整理时，读者可以在原话题指出具体哪句话概括不准；当前没有自动的“来源修改后提醒编辑”或“一键撤回全部引用”能力。

## 4. 新增真实活动和校园情况

先选定实际消息及其出处，再在 `community-topics.json` 增加 `kind: "event"` 或 `kind: "incident"` 的条目。帖子和评论本身不会自动创建活动、提取日期或更新状态；维护者核对后修改配置。活动与校园情况继续关联现有公开分类，原始讨论仍可保留。

以下只是字段模板，**没有对应真实活动或事件，不得原样作为生产内容发布**。尖括号是刻意保留的占位符，原样放入配置会校验失败；替换为真实信息，不知道的可选字段应省略，不编日期和地点。

```json
{
  "id": "<真实活动的稳定英文ID>",
  "catalogTopicId": "topic-clubs",
  "title": "<真实活动名称>",
  "prompt": "<消息出处、已知参与条件，以及欢迎补充的问题>",
  "kind": "event",
  "editorial": true,
  "event": {
    "status": "scheduled",
    "startsAt": "<真实计划开始时间，ISO格式并带时区>",
    "endsAt": "<真实计划结束时间；未知则删掉该字段>",
    "registrationStatus": "unknown"
  }
}
```

`event.status` 接受 `scheduled`、`postponed`、`rescheduled`、`cancelled`。改期时填新的 `startsAt`，已知原时间放入 `previousStartsAt`；新日期未定使用 `postponed`。报名独立记录 `registrationStatus: open / closed / unknown`，可补真实 `registrationStartsAt`、`registrationEndsAt`、`registrationUrl` 和最近状态核对的 `confirmedAt`。时间必须采用带时区的有效 ISO 时间，例如字段格式 `YYYY-MM-DDTHH:mm:ss+08:00`；页面按北京时间显示。

只有明确记录为开放、已有非未来确认时间、未到报名截止、活动时间允许且链接有效时，才显示“前往报名”。活动开始前可以不知道结束时间；开始后如果结束时间不明，不继续推断报名仍可进行。链接只接受无账号凭据的 HTTPS 公共域名地址，拒绝本地地址及字面 IP；网址格式通过不代表主办方或报名资格已经被核验。

```json
{
  "id": "<真实校园情况的稳定英文ID>",
  "catalogTopicId": "topic-campus",
  "title": "<具体情况和影响地点>",
  "prompt": "<已有消息出处、影响范围及欢迎补充的后续>",
  "kind": "incident",
  "editorial": true,
  "incident": {
    "status": "unknown",
    "occurredAt": "<已知发生时间；未知则删掉该字段>",
    "updatedAt": "<这次实质信息更新时间>",
    "summary": "<明确已知与尚未确认的部分>"
  }
}
```

`incident.status` 接受 `ongoing`、`resolved`、`unknown`。`updatedAt` 是信息编辑更新时间；`confirmedAt` 是实际核对状态的时间，两者不能互相代替。只有取得相应依据后才记录 `resolved` 并提供真实 `confirmedAt`。这可以是一位提供者在特定地点和时刻的观察；整理时保留观察范围，不能自动扩大为全校恢复。

## 5. 时效与历史的处理

| 情况 | 当前页面应呈现的意思 | 编辑动作 |
| --- | --- | --- |
| 报名截止，活动尚未来到 | 报名截止，活动仍按计划记录 | 保留活动页及后续讨论 |
| 活动改期 | 新计划与已知原计划并列 | 更新新时间，核对报名安排，保留变更出处 |
| 日期未定的延期 | 新时间待定、暂停报名 | 不因为旧日期过去就自动结束事件 |
| 活动取消 | 突出取消，停止报名 | 保留原消息和取消说明，允许之后回顾／纠正 |
| 已过计划结束时间 | 举办情况待确认，不声称实际举办成功 | 保留历史并补充真实回顾；不要制造参与人数 |
| 原定开始时间已到，但结束不明 | 现场情况待确认 | 不自动宣称已结束 |
| 校园情况长期没有新信息 | 显示最新记录及其确认时间 | 主动补充后续，不凭等待时间标成已解决 |
| 旧消息有新评论 | 讨论更新，不是活动发生时间改变 | 原活动日期保持不变 |

配置保留的历史条目仍能打开，过去不自动删除，原讨论也不会因超过计划时间就自动关闭。当前尚没有独立的活动归档库或自动活动状态采集；“历史”表示记录继续可查，不是已经确认活动实际举办。

## 6. 更新与验证

修改共建配置或页面代码后，先运行：

```powershell
node --test tests/topic-model.test.mjs tests/search.test.mjs tests/pages-build.test.mjs tests/pages-reviewed.test.mjs
npm run build:pages
```

代码和话题配置需要通过仓库部署流程更新；`npm run sync:pages` 只负责同步公开资料快照，不会顺带发布新话题配置、表单或界面代码。已经审核发布的资料应依照 [Pages 同步](github-pages.md) 更新快照。GitHub Actions 完成部署后，再检查实际公开页面。

每次活动改期／取消或采用贡献后，检查原链接、当前状态、报名动作和精确来源回链。没读到内容就保留空态；网络失败就说明未读到；还没有共同整理就展示相关背景资料。不要为了填满新界面伪造评论、参与者、热度、活动或核验记录。
