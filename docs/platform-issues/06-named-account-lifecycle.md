# [Platform] 补齐具名账户凭据维护与可恢复的账户生命周期

已提交：[decentralized-information-community #8](https://github.com/BillShiyaoZhang/decentralized-information-community/issues/8)，2026-09-09。

验收：runtime 0.3.0 已通过 6 项账户维护与 7 项恢复独立测试，见 [验收记录](../platform-reassessment-runtime-0.3.0.md)。2026-09-10 经仓库所有者授权发布 [验收评论](https://github.com/BillShiyaoZhang/decentralized-information-community/issues/8#issuecomment-5605444135)，并关闭为 completed。以下保留原始适配请求。

## 背景与精确基线

指南已固定消费 core/runtime 0.2.0，#7 的邀请参与者闭环验收通过。当前默认入口不再实现通用存储、会话或加密；准备退役旧应用时，逐项对照既有账户安全流程，发现本轮遗漏的具名账户维护契约。

基线是 `a436f19e60cb8c395a2c3e986e20d4c4d001b931` 之上的本地未提交 runtime 0.2.0 工作区，而非声称 GitHub 该提交已包含所有修复。已验证的 `packages/runtime/auth.mjs` SHA-256 为 `7EDD5A1F1975344468B63D73D984A4F3DAB20BA319C3EA29C531FE34F8362211`。本地安装的固定分发包与相邻源码均缺少下述维护操作。

指南现有产品边界包含账户自己的密码更换、TOTP/恢复渠道、管理者调整角色/停用，以及全部设备撤销。这不是要求保留旧账户管理网页，也不要求沿用原 PBKDF2 算法；受审计的离线 SDK/CLI 或可运行的外部身份服务集成都可以。

## 已支持的部分

- `bootstrapAccount` 可新建具名密码/TOTP 账户。
- `login`、`revokeSession`、`revokeIdentitySubject`、`invalidateIdentityCredentials` 支持登录、会话退出、主体撤销及全局凭据失效。
- `localIdentityProvider` 与 provider hooks、参与者会话及恢复挂钩已经存在。

这些能力有效，不能把“缺少凭据维护”描述为“没有会话撤销”，也不需要重开 #7。

## 已确认的限制

1. `bootstrapAccount` 是创建接口，同一稳定账户 ID 更换密码或 TOTP 返回 `ACCOUNT_EXISTS`；不能用来维护既有账户。
2. 密码派生与 MFA 密文写入均在 auth 模块内部。公开 SDK/HTTP/CLI 没有既有账户的密码轮换、MFA 重置或恢复操作；`login` 只接受六位 TOTP，没有恢复码或等价的可消费恢复流程。
3. 没有公开账户角色调整和可恢复停用/重新启用契约。`revokeIdentitySubject` 在指南启用全部五个模块的组合中会停用具名账户，并建立永久撤销墓碑；之后同 ID bootstrap 返回 `SUBJECT_CONFLICT`。仅启用 content/auth 时返回 `ACCOUNT_EXISTS`，同样不是重置接口。这适合永久撤销，不能等同于普通停用后重新启用。
4. 当前 provider hooks 覆盖验证/撤销/恢复，但没有交付能够替代上述账户维护的具体集成。要求消费者自己维护凭据发行、更换及恢复，会再次把通用账户系统留在数据/业务仓库。

合成内存诊断 8/8 通过：首次 bootstrap 和登录成功；同 ID 重新 bootstrap 为 `ACCOUNT_EXISTS`，旧凭据与旧会话未改变；指南五模块组合的主体撤销后会话确实失效，但同 ID 重新建立账户为 `SUBJECT_CONFLICT`。这是对现状/缺口的断言，通过不代表已经支持维护。未使用真实账号、密钥或数据库。

## 请求的最小契约

- 保持稳定 actor/account ID 的既有账户凭据维护：至少支持安全的密码更换和 MFA 凭据更换/恢复。可以采用具名受信离线操作，或要求旧密码及当前 MFA 的自助操作；不要求开放匿名找回密码接口。
- 原子完成凭据更新、目标旧会话/恢复凭据失效和审计；失败或并发冲突不得半更新。审计及可重放结果不得保存密码、TOTP 密钥、明文恢复码。
- 明确 MFA 丢失后的恢复机制。可选择一次性恢复码、可审计管理员重新引导，或已验证的外部 IdP；不能要求使用方自行修改 MFA 密文。
- 账户角色/状态变更与凭据维护分离。普通停用及重新启用不等于永久隐私撤回；状态和权限变化及时影响既有会话，不得使永久撤回主体重新激活。
- 明确备份恢复策略：恢复后不能静默使已替换的泄露凭据重新可用。可采用当前凭据撤销清册，或恢复后强制受审计的重新引导。

同类非阻塞补项：目前未兑换邀请只能按主体一起永久撤销；可以考虑独立取消一张错误签发的邀请，不影响该主体其他合法设备和邀请。此补项不否定 #7 已验证的单次兑换及主体撤回能力。

## 验收

- [ ] 独立消费固定包，为同一 actor ID 完成凭据轮换，原审计/内容归属不变。
- [ ] 旧密码、旧 TOTP/恢复能力及需撤销的旧会话不再可用，新凭据可正常认证。
- [ ] 未授权调用、错误旧凭据/MFA、并发冲突、重复请求及恢复码重放不会导致部分更新或泄漏秘密。
- [ ] 角色调整、普通停用/重启用与永久撤回具有明确不同语义，不能靠重新启用复活撤回主体。
- [ ] 恢复旧备份后的凭据处置有明确安全策略和回归测试。
- [ ] 示例使用 SDK/CLI 或真实 provider 集成，不需消费者直接修改 `auth.accounts`、密码散列、MFA 密文及会话内部数组。

业务仓库仍负责校园角色名称、授权审批、身份核验标准和必要页面。来源审核理由、内部备注规则、队列展示、争议警示与统计口径属于消费者待办，不包含在此平台需求中。
