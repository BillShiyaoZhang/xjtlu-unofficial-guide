## 验证依据

本轮仍针对根 lockfile 固定的 runtime 0.2.0 分发包。它来自上游 `a436f19e60cb8c395a2c3e986e20d4c4d001b931` 之上的本地未提交修复，不代表该 Git 提交已包含修复；精确包来源见 [产物记录](../vendor/README.md)。账户模块与相邻源码内容一致。

执行 `node --test docs/platform-probes/runtime-0.2.0-account-lifecycle.test.mjs`，**8/8 通过**。这是现状诊断，不是账户维护能力已通过验收：

- 已有账户再次 bootstrap 返回 `ACCOUNT_EXISTS`，旧凭据和会话保持不变。
- 单设备撤销、全局会话失效均有效，不应被误报为缺失。
- 仅启用 content/auth 时，主体撤销后不能通过同 ID bootstrap 重置账户。
- 指南五模块组合中，主体撤销使会话失效并留下永久墓碑；同 ID bootstrap 返回 `SUBJECT_CONFLICT`，不是普通停用后重新启用。
- 官方恢复使旧会话失效，但恢复的密码/TOTP 仍可登录，因此需要明确未来凭据轮换后的恢复策略。
- 合成恢复码不能替代 TOTP；候选账户维护 HTTP 路由返回 404，结合公开导出、CLI 与认证源码检查，未找到替代操作。

探针只使用合成内存状态、临时测试目录及测试凭据，没有读取或转换真实数据库。此前消费端 56/56、平台 120/120 与构建验收记录仍见前轮报告，本轮没有重跑这些完整套件。

## 旧实现保留方案

`apps/web` 目前有 268 个跟踪文件。新入口唯一仍执行读取的旧树依赖是迁移测试的 15 个 SQL schema 文件，可在恢复重构后移到独立测试 fixture 并调整测试路径；不能直接删除后宣称测试独立。

旧树下存在本地 SQLite 及 WAL/SHM、生成缓存和用户既有未提交修改。此次只检查路径与元数据，没有读取真实库，也没有删除、移动、暂存或覆盖旧文件。不能假定旧进程已经停止。

后续退役应先完成平台及业务验收，再把 schema fixture 从应用源码中分离，并采用保留本地旧目录、仅从 Git 跟踪中移除的方式保护旧库及用户改动。执行前检查暂存区和用户文件指纹，执行后复核并更新历史文档来源。此方案本轮未执行，也没有创建提交、部署或切换流量。
